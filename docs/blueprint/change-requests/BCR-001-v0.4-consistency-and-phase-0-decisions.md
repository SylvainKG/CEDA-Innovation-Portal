## Part B — Functional gaps found while reading (team decision needed)

| # | Gap | Evidence | Options | Recommendation |
|---|---|---|---|---|
| B1 | **The state machine has no exit from a clarification.** §4.3 says only `submit_revision` leaves `action_required`. Demo step 5 needs the case to go back to screening after the applicant replies | §3.2 step 5; §4.3; D-21 | (a) `respond_clarification` moves `action_required` → `return_stage`, same as `submit_revision`. (b) Clarification does not change status at all | **(a)**. It matches the applicant label "Action required: answer a question" (spec §6), which must clear once they answer. Add to §4.3: "`respond_clarification` moves `action_required` → `return_stage`" |
| B2 | **Same submit key, different content has no error code.** §4.4's error list does not cover reusing a `client_request_id` with different content | §4.4; evidence skill principle 8 | (a) Add `REQUEST_CONFLICT`. (b) Silently return the original reference | **(a)**. Add `REQUEST_CONFLICT` to the §4.4 error list for `submit_proposal` and `submit_revision` |
| B3 | Evidence skill proposes a generic `command_receipts` table for every workflow RPC | `security-and-reliability.md`, "Reliability application" | (a) Adopt for all RPCs. (b) Keep `client_request_id` on submit/resubmit only; other RPCs rely on conditional status updates, so a repeat returns `INVALID_STATE` and changes nothing | **(b) for the MVP.** Every transition RPC is already guarded by `WHERE status = $expected`. Record (a) in the debt register with the trigger "a non-transition command needs safe retry" |
| B4 | `email_outbox.status` `pending/sent/failed` overstates what is observed | Same file; principle 2 | (a) `pending · accepted · rejected · retryable · unknown_outcome` + `attempts`, `last_attempt_at`, `next_attempt_at`. (b) Keep v0.3 | **(a).** It is cheap (one enum and three columns, all in migration 001) and keeps the UI honest ("Email accepted by provider", never "Email sent") |
| B5 | Evidence skill proposes `proposals.row_version` for optimistic locking | Same file | (a) Adopt. (b) Defer | **(b) Defer.** Status transitions are already conditional updates. The only remaining case is one applicant autosaving a draft from two tabs; accept last-write-wins and record it as debt |
| B6 | Spec Q2: when does the applicant see reviewers' task verifications? | Spec §7 T08, §11 Q2 | Hidden until the decision is published / visible at once | **Hidden until publication** (spec default). It avoids early signals of the outcome |
| B7 | Spec Q3: spread-flag threshold | Spec §5 ScorePanel, §11 Q3 | ≥ 2 / ≥ 3 | **≥ 2** on the 1–5 scale (spec default) |
| B8 | Spec Q6: does the applicant bottom nav include Chat? | Spec §11 Q6 | Both / launcher only | **Both** (spec default) |
